включает создание и модерацию отзывов, агрегаты, поиск по опубликованным
материалам, Review Summary и использование отзывов в консультации. Хост
предоставляет товары, покупки, пользователей, права и AI. Проверен backend
на базе `fb5f4b8a28bdda3001a50709a8b0801a2637e6d1` с изменениями коммита,
содержащего этот отчёт. Frontend проверен на
`21deb66d2adf96c224151e559443ab4707875d2f`. Обе ветки
`feature/review-intelligence-v2`.

`RELEASE_GATE` — **NOT READY** для поставки в другой магазин. Прикладной
набор прошёл на настоящих изолированных сервисах. Доказана переносимость
выделяемого генератора Summary в проверенных границах. Жизненный цикл и
воркеры по-прежнему зависят от схемы и сервисов хоста. Полный ручной запуск
с настоящей аутентификацией требует отдельного изолированного профиля.

Прикладной прогон покрывает:

- Nest HTTP и PostgreSQL. Синтетическая идентичность подставляется вместо JWT,
  действует настоящий RolesGuard. Проверены доставка, принадлежность покупки,
  валидация, создание PENDING, одобрение, отклонение, модерация дополнения,
  удаление и повторная публикация. Проверены приватный owner view, статистика,
  конфликт параллельного создания, ограничения unique/check/FK и откат
  счётчиков после отказа FK. Параллельные голоса и модерация сохраняют
  согласованное состояние, конфликт Serializable возвращает 409.
- Qdrant. Настоящие именованные dense и BM25, keyword payload indexes,
  upsert, hybrid retrieval, проверка productId и embedding space. PostgreSQL
  скрывает PENDING, REJECTED, чужой товар и устаревшие публикации, даже если
  индекс возвращает поддельные ссылки. Дополнение в 4000 символов передаётся
  целиком в тестовый embedding. Повторная индексация, удаление точек, отказ
  Qdrant на неверной размерности, backoff и поздняя запись проверены.
- Review Summary. Пороги 9/10/19/20, независимость дополнений, single call и
  map/reduce, настоящий lease и heartbeat в течение 40 секунд, второй воркер,
  transient failure, повтор и отмена результата после удаления. Правило
  100 → 110 проверено отдельно на генераторе.
- Restart. Оба сервиса остановлены и запущены runner с прежними томами.
  Набор заново аттестует адреса и создаёт экземпляры воркеров. Сохраняются
  индекс и pending-задания, истёкшие lease подхватываются. Даты nextAttempt
  и истечения lease для отдельных сценариев выставляются в тестовой БД,
  чтобы воспроизвести ожидание и потерю процесса без долгих пауз.
- ProductAgent. Реальные catalog и review adapters. Рейтинг меняет порядок
  близких кандидатов, сохраняет заметный разрыв и не пропускает недоступный
  товар из устаревшего индекса. Compare читает mean, Recommendation получает
  статистику и готовую Summary за один синтетический вызов, Q&A возвращает
  источники выбранного товара. Некорректные позиции отклоняются, удаление
  во время генерации скрывает ответ, пустой корпус обходится без LLM.

Подставлены AI, оценки reranker и идентичность в тестовом HTTP-модуле.
Поведение реального токенизатора, размерность ответа провайдера, качество
модели и полный browser → JWT → AppModule этим прогоном не установлены.
Платных вызовов не было. Записи создавались только в выделенном стенде.
Проверена точная очистка строк и точек синтетического набора.

## Исправления

Обе регрессии воспроизведены до исправления на реальной БД.

- **P2, Review Summary.** Удаление учтённого отзыва отзывает lease и сбрасывает
  счётчик. Старый обработчик сбоя считал задержку из нулевого счётчика и
  передавал Prisma `Invalid Date`. После исправления он выходит, когда
  claim отозван. Новое задание сохраняется и успешно генерирует сводку.
- **P2, Review Index.** Новый worker завершал публикацию, пока старая запись
  ожидала ответа Qdrant. В тесте старая точка записывается реально, затем
  подставляется потерянное подтверждение. Компенсация удаляет старую точку,
  а новый claim остаётся нетронутым. Задержка в обоих обработчиках ограничена
  допустимыми индексами даже при сбросе счётчика активного задания.

Код исправлений расположен в
[ReviewSummaryService](../src/modules/reviews/review-summary.service.ts) и
[ReviewIndexService](../src/modules/reviews/review-index.service.ts).
Prisma schema и миграции совпадают с baseline.

## RELEASE_GATE

Текущий путь проходит от Review HTTP и ProductAgent к `ReviewsService`,
Prisma и записям текущего магазина. Публикация записывает задания для
`ReviewIndexService` и `ReviewSummaryService`. Воркеры используют
PrismaService, QdrantService и AiService. PostgreSQL хранит состояние
публикаций и заданий, Qdrant хранит поисковые ссылки. При выдаче источники
повторно проверяются в PostgreSQL.

Проверка переносимости исполнила исходный `review-summary.model.ts` в
изолированном JS-контексте, где разрешены только `node:crypto` и `zod`.
Один контракт проверен на строках реального Prisma и на независимом
JSON Lines-источнике с другими полями и ID. Оба дали те же входные тексты,
валидный ответ, проверки lease и порог 110. Второй маппер исключил
дубликат, удалённый материал и запись без ID. Этот результат относится
к runtime генератора и его каноническому входу. Тип `AiService` всё ещё
используется в TypeScript, а подключаемого порта источника отзывов для
жизненного цикла и воркеров нет.

**P1 для поставки.** В `ReviewsService.findDeliveredPurchase` право на отзыв
зависит от формы текущего заказа и статуса `DELIVERED`. Воркеры связаны с
таблицами Prisma и сервисами хоста. Другой магазин не может предоставить
покупку и корпус через имеющийся нейтральный контракт. Это блокирует
утверждение о переносимости продукта. Доказательства приведены в матрице
B/C и ограниченной проверке генератора.

**P2 для ручного запуска.** `QdrantModule` передаёт клиенту URL и timeout.
Изолированный Qdrant требует ключ. Функциональный набор передаёт
`qdrantApiKey` из аттестованного callback напрямую. Штатный AppModule
требует тестового wiring клиента и других внешних зависимостей. Отдельный
реальный запрос `getCollections` клиентом без ключа получил HTTP 401.

Для следующего согласования достаточно определить границу проверки покупки
и публикаций, оставить действующий Prisma адаптер, подключить второй
источник другого формата и прогнать тот же контракт жизненного цикла.
Отдельно нужен тестовый профиль полного запуска с изолированным Redis и
детерминированным AI. Эти шаги меняют архитектуру или конфигурацию поставки.

## Безопасный запуск для ручной проверки

1. В существующем backend worktree запустите и мигрируйте выделенный проект
   по [инструкции runner](../infra/integration/README.md). Используйте
   `ready` для текущих loopback-портов. Получайте `databaseUrl`,
   `qdrantUrl` и `qdrantApiKey` внутри `withServices`. Контрольный
   автоматический прогон доступен сразу.
2. Для полноценного backend подготовьте отдельный конфигурационный процесс
   с `POSTGRES_URI` из runner и тестовым `QDRANT_CLIENT`, которому передан
   ключ. Подготовьте отдельный Redis для `REDIS_URI` и параметров
   `REDIS_HOST`/`REDIS_PORT`, синтетические ключи JWT и сессии, безопасные
   подставные внешние сервисы. Подключите детерминированный AI в том числе
   для интерактивных Recommendation и Q&A. Флаги `REVIEW_INDEX_ENABLED` и
   `REVIEW_SUMMARY_ENABLED` управляют только фоновыми воркерами. Штатная
   точка входа Nest использует порт 5000 и CORS `CLIENT_URL`. Перед её
   запуском проверьте, что порт свободен и весь профиль указывает на
   тестовые сервисы. Полный профиль пока не подтверждён.
3. В frontend worktree задайте `NEXT_PUBLIC_SERVER_URL` и `BACKEND_URL`
   адресом подготовленного тестового backend, `JWT_SECRET` тестовым
   ключом проверки JWT. Запустите `npm.cmd run dev -- --hostname 127.0.0.1
   --port <свободный-порт>`. Этот origin должен совпасть с `CLIENT_URL`.
   Для Cypress вместо backend обе переменные адреса указывают на origin
   Next с суффиксом `/__review-test-api`, а API перехватывает spec.
4. Для ручного прогона нужны синтетические Client и Manager, товар, его
   DELIVERED-заказ покупателя и опубликованные материалы. Проверьте
   страницу товара, `/admin/reviews`, сравнение и вопрос об опыте.
   Автоматические fixtures удаляются после каждого прогона. Ручные
   записи подготавливаются отдельно в тестовой БД.

Автоматическая проверка готова. Cypress позволяет проверить браузерные
сценарии на синтетическом API. Готовность полной ручной интеграции остаётся
ограниченной условиями выше.
