# План Shared Integration Test Environment

Режим `REUSABLE_PRODUCT`. Ветка `codex/shared-integration-environment`, baseline `777498127d8cc29c29d254e2a314d07a07b020d7`. В этом коммите доступны актуальные для задачи миграции Support Handoff и Order Refund. У исходного detached HEAD `b23a3bb` те же файлы приложения, Prisma-схемы и миграций. Его отличие включает Harness Agentic Memory, поэтому инфраструктурная ветка основана на родительском коммите.

## Устройство

1. В `infra/integration` отдельный Compose project `support-engine-it-<12hex>` поднимает PostgreSQL 15.18 с pgvector и Qdrant 1.19.0. Суффикс вычисляется из канонического пути worktree, поэтому разные checkout имеют разные ресурсы. Compose хранит данные в двух собственных volumes, присоединяет контейнеры к выделенной bridge-сети и выделяет свободные loopback-порты при запуске. Health checks проверяют PostgreSQL по TCP и Qdrant по HTTP `/readyz`. Корневой Compose продолжает обслуживать обычную разработку.
2. Локальный Node.js runner обращается к явно проверенному локальному Docker context и задаёт окружение дочерних процессов. Адреса тестовых сервисов выводятся из проверенных port bindings. Для PostgreSQL проверяются имя БД, роль и соответствие системного идентификатора через хостовый порт и внутри контейнера. Для хостового SQL используется `pg` той же версии, что зафиксирована в существующем lockfile. Тестовые учётные данные уникальны для project. Для Qdrant проверяются адрес, доступ по тестовому ключу и отказ с неверным ключом. HTTP-запросы идут напрямую. Маркировка project, сервисов, сети и volumes позволяет отказать при конфликте ресурсов.
3. Мигратор копирует только проверенные Prisma-схему и миграции хоста во временный каталог, откуда запускает локальную Prisma CLI с явным тестовым `POSTGRES_URI`. Этот способ сохраняет историю миграций и отделяет её выполнение от рабочих `.env`. Ошибка `prisma migrate deploy` блокирует подготовку прикладных данных и отражается в отчёте.
4. Прикладные фикстуры используют данные Support Engine. У коллекций `products` и `store_knowledge` проверяется конфигурация именованных `dense` и `bm25` векторов. Smoke запускается поверх реальных сервисов и использует только синтетические данные. Независимый временный хост с собственной Prisma-схемой и другой формой данных проверяет переиспользуемую часть стенда без изменений runner.
5. Действия доступны через `npm run integration -- <action>`. `up` запускает Compose, `ready` подтверждает готовность и изоляцию, `migrate` применяет миграции, `collections` и `seed` подготавливают данные, `test` запускает smoke с прикладными фикстурами, `contract` проверяет контракты сервисов независимо от прикладной схемы. `stop` сохраняет данные. Явная команда `reset` проверяет принадлежащие проекту контейнеры и точный список volumes, при необходимости запускает ранее остановленные ресурсы для проверки обоих живых сервисов и только после этого удаляет тестовые volumes. При конфликте или неполном составе ресурсов операция завершается ошибкой. Операторская инструкция описывает запуск, диагностику и работу с фикстурами.

Фиксированные хостовые порты упростили бы внешнее подключение, но могли бы занять порт другого процесса. Docker выдаёт свободные порты, а runner проверяет их и сообщает потребителю. Текущий `qdrant:init` зависит от вызова embedding-провайдера, поэтому конфигурация коллекций задаётся детерминированно. Использование тестового ключа Qdrant требует передавать ключ в создаваемый тестовый клиент, в том числе при подмене провайдера `QDRANT_CLIENT` в Nest-тестах.

## Этапы и проверки

| Этап | Свидетельство |
| --- | --- |
| `DESIGN_GATE` | Границы хоста и стенда, допустимые адреса, стратегия изоляции, план диагностики миграций и проверки переносимости |
| Изоляция и запуск, `MILESTONE_GATE` | Конфигурация Compose, реальные healthy-контейнеры, портовые привязки, метки ресурсов и отказ при несовпадении окружения |
| Миграции, фикстуры и smoke, `MILESTONE_GATE` | Журналы Prisma, CRUD, ограничения, изоляция и rollback в PostgreSQL, векторный поиск, фильтрация и удаление в Qdrant |
| Воспроизводимость и `RELEASE_GATE` | Повторный запуск, штатная очистка, чистый повтор, независимая структура данных и сверка состояния рабочих контейнеров и volumes |

Пройденные проверки фиксируются с версиями, командами и фактическими результатами. До успешной обязательной проверки и проверки diff локальный коммит не создаётся.
