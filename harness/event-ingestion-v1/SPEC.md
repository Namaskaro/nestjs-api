# Support Engine — Event Ingestion V1

**Статус** — первая редакция требований к пилоту NextShop + WooCommerce. Разделы 1–9 фиксируют границы и проверяемые требования. Раздел 10 содержит решения, которые предстоит согласовать. Названия полей ниже описывают логический контракт. Точные DTO, транспорт и схема хранения утверждаются в PLAN.

**Основания** — Universal Event Ingestion Portability Discovery и завершающее ревью пилота из чата «Исследовать универсальный сбор событий» (`01a1dbb3-21fc-71d2-be3c-b194d9ab0ead`), предшествующие Discovery и Architecture Design Review по Recommendation Intelligence, [Architecture Contract](../../.agents/skills/support-engine-productization/architecture-contract.md) и [Portability Checklist](../../.agents/skills/support-engine-productization/portability-checklist.md).

Базовая ревизия для сверки с кодом — `integration/support-engine-v1`, `9b8098e703372aaa35b752a213f7b80fe615e5b0`. Существующий [`StoreEventV1`](../../src/user-context/user-context.contract.ts#L54) описывает `consultation.preference_confirmed`. В проверенном коде он объявлен как тип User Context. Канонический контракт Ingestion принадлежит Event Ingestion.

## 1. Назначение и владельцы данных

Event Ingestion принимает, проверяет и нормализует события, устойчиво записывает канонические факты в PostgreSQL и делает их доступными разрешённым обработчикам. Он обеспечивает происхождение, дедупликацию, повторную доставку, сверку состояния и соблюдение срока и цели обработки.

- Магазин владеет аккаунтами, каталогом, корзиной, заказом и его статусами. Адаптер знает протокол, права, возможности установки, местные ID и правила маппинга. Служебный снимок заказа и чтение заказа покупателем используют разные полномочия.
- Core задаёт каноническую семантику и инварианты. Application координирует приём, запись, доставку и отзыв через проверяемые границы. NextShop, WooCommerce, WordPress, NestJS, Prisma и PostgreSQL подключаются через адаптеры или сборку. PostgreSQL — внутренний профиль хранения Engine.
- User Signals в будущем выводит интересы и намерения из фактов. User Context остаётся владельцем подтверждённых предпочтений. Agentic Memory владеет эпизодами и продолжением задач. Recommendation Engine выбирает, оценивает и показывает кандидатов.
- В пилоте проверяется эффект обработчика на одном тестовом потребителе проверенного `category.viewed`. Он демонстрирует появление краткоживущей записи по категории, её истечение и отзыв. Продуктовые User Signals, запись предпочтений, ранжирование, рекомендательный UI и алгоритмы персонализации относятся к следующим задачам.

## 2. Канонический контракт и данные для потребителей

| Поле или группа полей | Требование |
| --- | --- |
| `eventId`, `type`, `schemaVersion` | Стабильный ID логического события при повторной доставке, тип и версия его конверта и полезной нагрузки. Payload валидируется по паре «тип, версия». Неизвестный тип, версия и неподдерживаемая возможность различимы. |
| `tenantId`, `storeId`, `subject` | Доверенные ключи арендатора и магазина. Субъект — проверенный аккаунт, анонимная сессия магазина либо отсутствие подтверждённого субъекта у служебного факта. |
| `occurredAt`, `receivedAt`, `observedAt` | Время факта, если оно известно, и обязательное серверное время приёма. Для снимка обязательно время наблюдения. Для браузерного времени сохраняется его происхождение. Снимок не получает вымышленную дату перехода. Времена приводятся к UTC. |
| `provenance` | Установка и namespace источника, класс факта, доступный внешний ID логического события или перехода, ревизия объекта при наличии. ID попытки доставки учитывается отдельно. Типы фактов различают браузерное наблюдение, подтверждённый переход, наблюдение состояния и доверенное событие Engine. |
| `purpose` и основание обработки | Серверное решение о допустимой цели, с версией политики или ссылкой на актуальное разрешение. Для согласия и отзыва нужна различимая версия или поколение разрешения. |
| `payload` и связи | Минимальные поля конкретного типа. Ссылки на товар, вариант, категорию, заказ и позицию используют namespace источника. Точный вариант и позиция передаются при достоверном сопоставлении. Сессия и ключ задачи передаются, когда известны и проверены. |

Данные должны позволять будущему User Signals восстановить тип действия, объект, времена, источник и доступный контекст. Например, `product.viewed` хранит известный товар, вариант при наличии и сессию. Событие не устанавливает, понравились ли товар или бренд. Неизвестный вариант, связь с задачей и категория остаются неизвестными. Проекции получают различимые ссылки на исходные факты. Канонический журнал и диагностические записи исключают raw payload по умолчанию, поисковый текст, тексты чатов, email, order key и платёжные реквизиты.

Для каждого магазина и канала фиксируются доступные типы, класс источника и гарантии. Отсутствие поддержки, недоступность источника и отсутствие наблюдавшегося факта различаются.

## 3. Доверенные источники и принадлежность

- Серверный источник аутентифицируется и привязывается к зарегистрированной установке магазина. Woo-адаптер проверяет подпись по исходному телу и принадлежность подписки. Значения tenant, store, customer ID или класса факта из браузерного тела сами по себе полномочий не дают.
- Витрина сообщает наблюдения через контекст, выданный доверенным сервером. Проверяются срок и принадлежность сессии, тип, размер, частота и применимые ссылки на каталог. Валидная сессия подтверждает контекст посетителя. Успешная мутация корзины остаётся наблюдением витрины, если её сообщил браузер.
- При входе, выходе или смене аккаунта выдаётся новый контекст. Аккаунт связывается только с допустимыми новыми событиями после входа. Анонимная история остаётся в исходной области магазина. Email, IP, совпавшие ID или право прочесть гостевой заказ не служат основанием для склейки истории.
- Авторизованное чтение возвращает минимальный снимок одного заказа после актуальной проверки владельца. NextShop переиспользует проверку пары «заказ, доверенный пользователь». В текущем профиле гостевое чтение NextShop не поддерживается. Для гостя WooCommerce сервер магазина проверяет конкретный заказ, order key и непустой совпадающий billing email, затем выдаёт ограниченное по сроку, магазину, сессии и цели разрешение на этот заказ. Исходные credentials остаются у магазина. Ошибка проверки не раскрывает чужой заказ. [NextShop Order Adapter](../../src/modules/orders/adapters/current-store-order.adapter.ts#L98), [Woo Store API Order](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/order/).

## 4. Обязательный набор пилота NextShop + WooCommerce

Обе интеграции должны довести следующие факты от собственного входного формата до журнала и согласованного эффекта обработчика. Витринное подключение использует один независимый от UI-фреймворка контракт.

| Событие | Достоверная семантика и минимум данных |
| --- | --- |
| `product.viewed` | Наблюдавшийся просмотр карточки. Товар, вариант при наличии, контекст сессии. Фоновые загрузки и сам ответ API не устанавливают просмотр. |
| `category.viewed` | Наблюдавшийся просмотр категории, проверенной по каталогу магазина. Тестовый потребитель использует только это событие для демонстрации сигнала категории. |
| `search.submitted` | Факт отправки поиска. Исходная строка запроса не сохраняется. |
| `cart.item_added`, `cart.item_removed`, `cart.quantity_changed` | Наблюдение успешного действия витрины. Товар, вариант или идентификатор строки при наличии. Для изменения количества передаётся известное итоговое количество. |
| `order.paid` | Подтверждённый переход оформленного заказа в оплаченное состояние при доказанном полном списании в профиле пилота. Ссылка на заказ и идентичность перехода. Позиции, варианты и количества берутся из минимального авторитетного снимка либо передаются с событием, если известны на момент перехода. |
| `order.cancelled` | Подтверждённый сохранённый переход оформленного заказа в отменённое состояние. Ссылка на заказ и идентичность перехода. Отмена заказа и возврат денег имеют самостоятельную семантику. |

Для товарных событий категория берётся из проверенного каталога или из явного контекста страницы после проверки. При неоднозначности нескольких категорий адаптер сохраняет доступные связи или неизвестность. Он не выбирает первую категорию произвольно. Решение о проверенной категории сохраняется для воспроизводимого replay.

NextShop должен выпускать `order.paid` по сохранённому переходу `PENDING_PAYMENT → PAID` после подтверждения оплаты. Для `order.cancelled` покрываются обе действующие ветки отмены, включая резервирование возврата. У WooCommerce оплата требует доказательства полного capture от согласованного шлюзового пути, а отмена — подтверждения сохранённого перехода. Статус заказа, `date_paid_gmt`, уведомление `order.updated`, Checkout Blocks и вызов hook сами по себе не подтверждают списание или точную историю переходов. REST-сверка может восстановить доступный снимок, включая состояние оплаты или отмены, с указанием времени наблюдения. Она не создаёт задним числом `order.paid` или `order.cancelled`. [Подтверждение платежа NextShop](../../src/payment/payment.service.ts#L414), [Прямая отмена](../../src/modules/orders/adapters/current-store-order.adapter.ts#L192), [Отмена с возвратом](../../src/modules/orders/refund/refund.service.ts#L112), [Woo Webhooks v3](https://developer.woocommerce.com/docs/apis/rest-api/v3/webhooks/), [Woo Orders v3](https://developer.woocommerce.com/docs/apis/rest-api/v3/orders/).

Пилот включает защищённое чтение снимка заказа, сверку пропусков и наблюдение состояния подписки WooCommerce. Доставка товара, возврат позиции, отзывы, wishlist, произвольный backfill и подключение других платформ остаются за границей пилота.

## 5. Показы и клики по рекомендациям

Требования к будущим `recommendation.impression` и `recommendation.clicked` фиксируются сейчас. Они не добавляют обязательную инструментализацию витрины или отдельный источник рекомендаций в этот пилот.

- Показ означает наблюдавшуюся видимость конкретной карточки. Формирование списка, ответ API и отрисовка вне видимой области не создают показ. Нужны стабильные `impressionId` и `decisionId`, товар и известный вариант, поверхность, позиция и времена. Версия политики и происхождение кандидата передаются из доверенного контекста выдачи при наличии.
- Атрибутированный клик ссылается на тот же `impressionId` и `decisionId`. Проверяется принадлежность товару, магазину и разрешённому субъекту или сессии. Повтор доставки использует тот же ID, отдельное взаимодействие получает новый. Поздний показ и клик допускают проверяемое связывание. Клик без подтверждённой связи остаётся неатрибутированным, вымышленный показ не создаётся.
- Органическое открытие товара, клик по рекомендации и показ сохраняют разную семантику. Техническая корреляция оставляет будущему потребителю возможность выявить связанные наблюдения. Отсутствие клика не означает отрицательную оценку.

## 6. Идемпотентность и повторная доставка

- Уникальность логического события учитывает tenant, store, namespace источника и стабильный ID. Повтор с тем же значимым содержимым даёт результат `duplicate` без повторного эффекта. Тот же ключ с другим значимым содержимым — конфликт. Коррекция имеет свой ключ и ссылку на исправляемое основание или его ревизию.
- Попытка доставки, событие и бизнес-переход имеют отдельную идентичность. Несколько уведомлений об одном переходе сводятся к одному эффекту по стабильному ключу перехода. Это допускает две реально различимые отмены после восстановления заказа. Один Woo delivery ID недостаточен для установления уникальности перехода.
- Принятие подтверждается после устойчивой записи. Ошибки доступа, формата, конфликта и отсутствия возможности отличимы от временной недоступности. При приёме пакета результат определяется по каждому элементу. Потерянное подтверждение допускает безопасный повтор.
- Гарантия доставки обработчику — `at-least-once` для принятого события в рамках разрешённых сроков. Эффект идемпотентен по идентичности потребителя и логического события внутри магазина. Глобальный порядок не гарантируется. Поздние факты не должны откатывать более новую ревизию состояния. При отсутствии надёжного порядка требуется сверка у владельца данных.

## 7. PostgreSQL-журнал и обработчики

Журнал принадлежит Engine. Каноническая запись и долговечная возможность обработать её фиксируются согласованно. После сбоя между записью и доставкой принятая работа сохраняется. После сбоя между эффектом и подтверждением обработчик повторяет попытку без повторного эффекта. Для PostgreSQL-эффекта запись результата и отметка обработки согласуются в транзакции. Отдельный брокер для пилота не требуется.

Обработчики читают только свою область tenant/store и разрешённые цели, ограничивают объём работы и различают постоянные и временные ошибки. Требуются наблюдаемость задержки, повторов, исчерпанных попыток и конфликтов, а также управляемое повторное выполнение без раскрытия payload. Лимиты, backoff, формат изоляции отказов и ручное управление определяются в PLAN. Replay повторяет проверки права, срока и версии события. Сбой и перезапуск не должны продвигать позицию чтения за непринятую работу.

Сверка источника восстанавливает записанные переходы и независимо обновляет наблюдаемое состояние заказа. Отключение подписки WooCommerce обнаруживается по активной проверке её состояния и конфигурации. Одного отсутствия трафика недостаточно. Пропуск до долговечной записи на стороне Woo остаётся отдельным риском, требующим согласования.

## 8. Исправление, удаление и отзыв согласия

- Для версии факта сохраняется актуальное основание либо отметка отзыва. Исправление заменяет прежний эффект. Запоздалая версия, дубль или replay не возвращают отозванный вклад. Семантика коррекции доступна потребителю без передачи лишних персональных данных.
- Разрешение проверяется при приёме и непосредственно перед фиксацией эффекта. Событие, собранное по согласию, сохраняет поколение разрешения с момента захвата и при всех повторах. Отзыв согласия прекращает дальнейший сбор и публикацию для указанной цели. Выход из аккаунта закрывает контекст подачи и очищает буфер, а судьба ранее принятых данных определяется целью и сроком. Маркетинг требует самостоятельного разрешения.
- Доверенная операция удаления устанавливает барьер по области запроса и очищает связанные события, постановки на обработку, записи об ошибках, связи и тестовые производные. Обработчик, уже начавший работу, проверяет барьер при публикации. Повтор доставки из магазина, очередь, replay и восстановление бэкапа проходят те же ограничения. До применения более свежих барьеров после восстановления обработка остаётся закрытой.
- Срок минимальной информации для подавления повтора должен перекрывать допустимый срок источников повторной доставки и восстановления. Новое действующее разрешение допускает новые факты, сохраняя запрет на восстановление удалённой истории. Операционное чтение заказа действует по своему основанию и не питает персональные проекции без соответствующего права.

## 9. Критерии приёмки

Один параметризованный контрактный набор выполняется с рабочими адаптерами NextShop и WooCommerce по цепочке «собственный исходный формат → нормализация → PostgreSQL → потребитель». Замена адаптера не требует изменений Core/Application. Тесты используют изолированный [Shared Integration Test Environment](../../infra/integration/README.md) и реальные зависимости в утверждённом объёме.

| Проверка | Ожидаемый результат |
| --- | --- |
| Маппинг и версии | Оба адаптера доставляют весь обязательный набор. Позиция и вариант сохраняются при достаточных данных, отсутствующие связи различимы. Неизвестные типы и версии корректно отклоняются. Проверенный просмотр категории имеет воспроизводимый тестовый эффект. |
| Доверие и изоляция | Подделка tenant, пользователя, подписи, заказа или категории не даёт эффекта. Одинаковые внешние ID разных магазинов изолированы. Проверены аккаунт, гостевое чтение WooCommerce, выход, смена аккаунта и отсутствие склейки старой истории. |
| Заказы и сверка | Подтверждённые оплата и отмена доставляются. Черновик, авторизация без списания, финансовый refund и одиночный снимок не порождают ложные переходы. Пропуск после долговечной записи восстанавливается. Устаревший снимок не откатывает состояние. Отключённая подписка обнаруживается. |
| Повторы и сбои | Конкурентные повторы и потерянный ACK дают один эффект. Конфликт содержимого явен. Перезапуск до и после фиксации эффекта, временная недоступность и повторная обработка не теряют принятую работу. |
| Исправление и приватность | Проверены замена ревизии, отзыв источника и согласия, удаление при работающем обработчике, повтор, replay и барьер восстановления. Отозванная запись не появляется снова. |

Реальная поддержка WooCommerce подтверждается отдельно на согласованной изолированной установке с реальным Checkout Blocks и тестовым шлюзом. Синтетический источник с собственным форматом пригоден для проверки заменяемости адаптера, но не доказывает права, платёжную семантику и доставку реальной интеграции. `MILESTONE_GATE`, `PORTABILITY_GATE` и `RELEASE_GATE` оцениваются отдельно по зафиксированной ревизии и профилю. Доказательств прохождения на момент подготовки SPEC нет.

## 10. Открытые решения до утверждения PLAN

1. **Woo-профиль и доступы.** Подтвердить изолированный магазин, Checkout Blocks и HPOS, разрешение на установку плагина, версии WooCommerce и шлюза и один профиль автоматического test capture. В ревью предложены WooCommerce 11.3.0 и Stripe 11.1.1. Это предложение до проверки доступного стенда.
2. **Граница надёжности Woo-переходов.** Согласовать разрыв между сохранением заказа и долговечной записью перехода в журнал плагина. Предложение ревью — восстанавливать переходы после записи. До записи REST может восстановить лишь наблюдаемое состояние. Если нужна полная история через этот разрыв, потребуется доказанная атомарность у источника.
3. **Механизмы доставки и сверки.** Транзакционный outbox в обеих ветках NextShop, журнал переходов Woo-плагина, webhook как уведомление и независимый опрос предложены в ревью. В PLAN утвердить точки записи, ошибочные исходы, размеры и интервалы сверки, курсоры, ограничения повторов и диагностику. Там же закрепить точную форму envelope и снимка, namespace, версии и транспортные маршруты.
4. **Политика данных пилота.** Утвердить цели и допустимые основания, владелец операции удаления у каждого источника, сроки журнала, очередей, барьеров и резервных копий, а также способ восстановления с применением более свежих отзывов. Порог видимости и правила атрибуции показов остаются открытыми до подключения рекомендации.
