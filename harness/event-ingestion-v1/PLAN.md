# Support Engine — Event Ingestion V1

**Режим** — REUSABLE_PRODUCT. **Статус** — проект PLAN для согласования. Источник требований — [SPEC.md](SPEC.md), Universal Event Ingestion Portability Discovery и итоговое ревью в чате `01a1dbb3-21fc-71d2-be3c-b194d9ab0ead`. Базовый backend — `integration/support-engine-v1` на `9b8098e703372aaa35b752a213f7b80fe615e5b0`. До начала работы PLAN и STATE пусты, SPEC и документы Review Intelligence присутствуют вне индекса, изменений отслеживаемых файлов не обнаружено. Приведённые ниже wire-формы, имена таблиц, числовые бюджеты и архитектурные поправки предлагаются к утверждению.

## 1. Вердикт и замечания к SPEC

Общий движок на PostgreSQL подходит для изолированного пилота. Для NextShop можно записывать переход и запись outbox атомарно в одной транзакции магазина. Для WooCommerce гарантия полного ряда переходов пока не доказана. Обычный webhook и позднее чтение восстанавливают состояние, а промежуточная отмена с последующим восстановлением заказа может остаться неизвестной. До решения владельца продукта реализация реального Woo-профиля заблокирована.

Утвердить ограниченную гарантию для записанных переходов либо предъявить атомарный источник переходов и испытать его на разрыве. |

## 2. Поток, границы и предлагаемые контракты

```text
Действие витрины → независимый SDK и контекст магазина → Browser adapter
NextShop: переход и outbox в одном commit → relay       → Server adapter
Woo: журнал доказанных переходов → pull/ACK              → Server adapter
Woo: REST сверка → наблюдение состояния                 → Snapshot adapter
                         ↓
       Application: доверие → правила Core → журнал + работа
                         ↓
      worker: lease → повторная проверка → эффект + completion
```

- **Core** — смысл типов и версий, ключи области, классы происхождения, правила допустимости и сравнение версий. Чистые TypeScript-модели без DTO магазинов, NestJS, Express, ORM или SQL.
- **Application** — приём, выдача результата по элементу, доставка, исправление/отзыв, просмотр снимка с проверкой доступа. Использовать три внешние границы по потребности: доверенный контекст и право, чтение каталога/заказа, устойчивое хранилище с атомарными операциями. Контракт обработчика общий для тестового потребителя. Transport и планировщик подключаются в host.
- **Adapters** — NextShop разрешает JWT и гостевую область, читает каталог и владельца заказа, пишет transition outbox. Woo знает WordPress, HPOS, gateway evidence, гостевой grant, REST и журнал плагина. Секреты, настройки источников, схема данных и leases принадлежат адаптерам и инфраструктуре. Определение tenant и назначения запроса происходит на входной границе.
- **Семантика** — браузерное наблюдение, подтверждённый переход заказа и снимок состояния имеют разные входы и результаты. Канонический тип даёт факт и его основание. Единственная тестовая проекция по категории проверяет эффект, истечение и отзыв. Ветка User Context и её `StoreEventV1` остаются отдельными.

| Граница | Предлагаемая форма V1 |
| --- | --- |
| Витрина | `POST /v1/events/batch` с краткоживущим контекстом установки, сессии и поколения. Элемент содержит стабильный клиентский ID, тип, версию, время действия при наличии и разрешённые поля действия. Успешные результаты по элементу после commit — `accepted` или `duplicate`. Постоянные ошибки — `rejected` с машинным кодом, временная недоступность — повторяемый результат. Проверка прав предшествует сообщению результата дедупликации. |
| Серверные переходы | Типизированный вход `ingestTransition(trustedInstallation, transition)`, доступный из relay и Woo pull. Содержит ID заказа, тип, устойчивый ID перехода, подтверждённое время/ревизию, ссылки на позиции и доказательство, известные адаптеру. В журнал идёт минимальное каноническое описание. Отпечаток подписи или ID доставки не становится ID бизнес-перехода. |
| Снимок | Отдельная операция `getOrderSnapshot(context, orderRef)`. Снимок содержит источник и время наблюдения, состояние и минимальные позиции с количеством и известным вариантом. Операционные REST-чтения используют служебные полномочия. Пользовательское чтение требует свежей проверки заказа и контекста. Остальные поля магазина не возвращаются. |
| Хранение | Логический конверт из SPEC с версией payload по типу. `receivedAt` выдаёт сервер. Браузерное `occurredAt` имеет отметку доверия, а время наблюдения снимка задаётся отдельно. Tenant/store, источник и цель назначаются сервером. Сессия, задача и вариант учитываются только при достоверной связи. Возможности установки имеют состояния `supported`, `snapshot_only` и `unsupported`, временный отказ отдельный. |

Стабильный ключ приёма — `(tenant, store, sourceNamespace, sourceEventId)`. Сравнивать нормализованный авторизованный вход без серверного времени, транспортного номера и вычисляемого обогащения. На первом приёме закреплять проверенную категорию, версию маппинга и смысл поля. Так повтор после изменения справочника сохраняет результат. Для перехода дополнительно проверять уникальный ключ `(tenant, store, authorityNamespace, transitionId)` и совпадение значимых данных перехода. Источник исправления получает новый ID и ссылку на уже известную ревизию. Один transition ID сохраняется при всех повторах, а новая отмена после восстановления имеет собственный ID.

Для браузера использовать разрешённый срок захвата и отправки и фиксировать время/поколение при захвате. Изменение контекста закрывает прежнюю область. Для состояния с монотонной ревизией применять только актуальную версию. При отсутствии ревизии, например при равном `date_modified_gmt` и разных снимках Woo, назначить защищённое от устаревшего worker точечное перечитывание и применить его как новое наблюдение. Ревизия состояния и положение потребителя в журнале независимы. Номер строки или время действия не используются как глобальный безопасный watermark при конкурентном commit.

## 3. Предлагаемые файлы и миграции

| Место | Назначение |
| --- | --- |
| `src/event-ingestion/{core,application,ports}` | Конверт и типизированные payload, сценарии приёма, эффект, доступ и отзыв. Запрет транзитивных импортов хоста. |
| `src/event-ingestion/adapters/{postgres,nextshop,woocommerce,http}` и модуль сборки | Журнал, work, права и ревизии в PostgreSQL, адаптеры scoped identity, catalog/order и transport. Маршрут Woo webhook получает исходные байты до JSON-мэппинга. Текущий Nest bootstrap создаёт приложение без настройки `rawBody`. [main.ts](../../src/main.ts#L13) |
| `prisma/schema.prisma`, новая миграция Engine и отдельная миграция NextShop outbox | Добавочные таблицы и ограничения. Таблица outbox находится в той же БД и транзакции, что запись заказа. Core использует порт Engine; схема и Prisma живут в host. Роли и доступы проверяются в изолированном окружении. |
| `integrations/woocommerce/event-ingestion/` | Предлагаемое место PHP-плагина или каталог поставки в согласованном репозитории. Собственный журнал и минимальные HTTP-операции, Woo CRUD и совместимость HPOS. Миграция таблиц плагина отдельна от Prisma и разрешается только на утверждённом стенде. |
| `infra/integration/event-ingestion.test.cjs` и точечные Jest specs | Предлагаемый параметризованный runner поверх `withServices`, общие проверки и fixtures с реальной исходной формой. Клиент NextShop подключается из отдельного frontend checkout после утверждения каталога правок и исходной ревизии. |

Предлагаемые записи PostgreSQL:

- `ingestion_event` с нормализованным payload, правом/областью, сроком и ключами из §2. Уникальность транспортно-независимого события и частичная уникальность известного перехода. Индексы по области удаления, ссылке на позицию/заказ для служебных фактов с `subject:none`, сроку и ссылке исправления там, где нужен replay.
- `ingestion_work` с уникальным `(eventId, consumerKey)` внутри tenant/store, состоянием, попытками, сроком следующей попытки и lease token/expiry. Статус завершения является receipt для единственного транзакционного потребителя. Частичный индекс due по состоянию и `(nextAt, id)`. Ошибка или отложенная работа хранит машинный код и ссылку. Выделенная очередь с копией payload избыточна.
- Серверные ingestion-сессии и барьер `(tenant, store, subject, purpose)` с поколением и допустимостью. Тестовая проекция категории хранит ссылку на событие, срок и область. Снимок/позиция сверки хранят минимальное состояние, связь с заказом и версию или время наблюдения. Отдельное физическое партиционирование рассматривать после замеров retention и I/O.
- `nextshop_ingestion_outbox` содержит устойчивую идентичность, минимальные данные перехода и состояние передачи. Relay удаляет или закрывает запись по политике только после `accepted` или `duplicate`. Уникальность перехода сохраняется при повторном чтении. Включать capture/relay по профилю только после применения миграций.

Порядок миграций — сначала Engine, затем outbox в NextShop. Создать и применить в согласованной изолированной БД после разрешения. Проверить чистый запуск, повторный запуск и выключение при сохранённых таблицах. При откате выключить вход новой возможности и relay согласно правилам восстановления. Для профиля с гарантией capture перевод в обычный режим требует явной фиксации границы времени и остановки пилота. Удаление таблиц или данных выходит за рамки безопасного отключения.

| Сценарий | Текущее поведение и целевая точка |
| --- | --- |

Во frontend `refactor-client` на `integration/support-engine-v1` (`3b3b27f1177f4e03259b98cd2a244a745ebf71fe`) проверены `src/app/(root)/product/[id]/page.tsx` и каталог. [ProductsController](../../src/modules/products/products.controller.ts#L110), [Карточка и каталог](../../src/modules/products/products.service.ts#L552), [CategoriesController](../../src/modules/categories/categories.controller.ts#L24) |
| Корзина | `add` сохраняет строку с товаром и размером. Удаление и изменение количества идут через CartService. Actor для этих мутаций в исследованных путях не проверяется сервисом по паре «строка, владелец». UI использует `onSettled` для удаления и количества, поэтому успех надо определить по семантике ответа и обновлённой строке в той же разрешённой сессии. Пилот учитывает три наблюдения storefront. Для Ingestion брать владельца из проверенного контекста, а идентификатор варианта — только из достоверного каталожного маппинга. Гостевой checkout/cart и изменение правил авторизации корзины требуют отдельного scope. [CartController](../../src/modules/cart/cart.controller.ts#L88), [Изменение строки](../../src/modules/cart/cart.service.ts#L155) |
| Избранное | Защищённый `toggleFavorite` читает и обновляет отношение пользователя. Текущая операция toggle может менять значение при повторных действиях. В пилоте нет типа для избранного. Checkout переводит в PENDING_PAYMENT. Текущий `order.update` выполняется после чтений без общего lock. Рекомендуемый prerequisite для M3 — использовать ту же блокировку заказа, что оплата/отмена, с повторной проверкой владельца, статуса и платежа внутри транзакции. Добавить тест интерливинга с оплатой и отменой. Событие создания заказа вне V1. [Создание](../../src/modules/orders/orders.service.ts#L432), [Checkout](../../src/modules/orders/orders.service.ts#L587), [Write](../../src/modules/orders/orders.service.ts#L654) |
| Оплата | `createPayment` может установить Payment.SUCCEEDED из ответа провайдера без обновления заказа. `syncPaymentStatus` через JWT status-route читает YooKassa, сверяет ID, валюту и сумму с Payment, затем блокирует заказ владельца и применяет CARD + PENDING_PAYMENT → PAID. Добавить запись outbox прямо в этой транзакции на сработавшем переходе, вместе с очисткой корзины. Рекомендуется перепроверить под lock актуальную Payment, привязку и `Order.finalAmount` перед переходом. Поздний успех для CANCELLED обновляет платёж и сохраняет отменённое состояние заказа. Страница результата зависит от возврата покупателя. Существующий платёжный адаптер запрашивает `capture: true`. Отдельный серверный trigger для несинхронизированного списания требует решения O3. [Order Adapter](../../src/modules/orders/adapters/current-store-order.adapter.ts#L98), [Logout](../../src/modules/auth/auth.controller.ts#L69)

**Граница гарантии NextShop.** Запись outbox и commit бизнес-перехода имеют одну транзакцию с одним владельцем. При ошибке outbox локальный переход откатывается. После commit relay может передать запись повторно. Прямой HTTP emit или публикация только callback после commit оставляют окно потери. Периодическая сверка полезна для текущего состояния и операционных пропусков, но переход без outbox она задним числом не придумывает. Захват средств в YooKassa не атомарен с локальным commit, поэтому обещание относится к сохранённому переходу заказа.

## 5. WooCommerce — ограничения, варианты и предлагаемый профиль

По состоянию на 17 ноября 2026 опубликован WooCommerce 11.3.0. Для стенда предложен WooCommerce 11.3.0, HPOS, Checkout Blocks и официальный Stripe Gateway 11.2.0 с автоматическим capture в test mode. Исправленная 11.1.2 — допустимая альтернатива после согласования и повторной верификации. Исправленные версии требуют WordPress 6.9 и WooCommerce 11.0 или выше. Перед испытанием подтвердить конкретные версии, доступы и профиль карты. - **Webhooks и REST.** REST v3 используется с отдельным минимально привилегированным ключом установки поверх HTTPS. Webhook HMAC-SHA256 проверяется по raw bytes, привязке подписки и секрету установки. Заголовки доставки помогают диагностике, но не заменяют авторизацию или логический ключ. Штатные `order.created/updated/deleted` отражают уведомления о ресурсе. Путь доставки асинхронный и читает состояние при отправке. Различать приостановленную, отключённую, отсутствующую и недоступную для проверки подписку. Порог отключения и успешные коды не переносить из документации в гарантии Engine, поскольку реализация и настройки версии могут отличаться. [REST auth](https://developer.woocommerce.com/docs/apis/rest-api/authentication/), [Webhooks v3](https://developer.woocommerce.com/docs/apis/rest-api/v3/webhooks/), [WC_Webhook 11.3.0](https://github.com/woocommerce/woocommerce/blob/11.3.0/plugins/woocommerce/includes/class-wc-webhook.php)
- **Оплата, отмена и Blocks.** Store API checkout hook до оплаты, ручной статус, `date_paid_gmt`, transaction ID и вызов `payment_complete` отдельно недостаточны. Проверять доверенное и связанное доказательство подтверждённого полного capture по сумме, валюте и тестовому профилю, сохранённый заказ и переход. Исходная точка для Stripe — проверенная ветка `wc_gateway_stripe_process_response` или другой доказанный путь выбранного шлюза. Подтвердить привязку Charge/Intent к заказу и gateway account, `captured`, статус, полную сумму, валюту и сохранённое состояние. Для отмены использовать зафиксированный from/to и независимую проверку сохранённого состояния через Woo CRUD. В проверенном коде ошибка `save()` может быть перехвачена до вызова callback. Сам callback и объект в памяти не доказывают commit. Refund, черновик, удаление, авторизация без capture и no-payment checkout имеют собственную семантику. Нет команды оплаты или отмены со стороны Ingestion. [Hooks Checkout Blocks](https://developer.woocommerce.com/docs/block-development/reference/hooks/hook-alternatives/), [WC_Order 11.3.0](https://github.com/woocommerce/woocommerce/blob/11.3.0/plugins/woocommerce/includes/class-wc-order.php), [Обработка ошибок Woo save](https://github.com/woocommerce/woocommerce/blob/11.3.0/plugins/woocommerce/includes/abstracts/abstract-wc-order.php#L261-L322), [Stripe Gateway 11.2.0 — платёжная ветка](https://github.com/woocommerce/woocommerce-gateway-stripe/blob/11.2.0/includes/abstracts/abstract-wc-stripe-payment-gateway.php#L657-L733), [Stripe test mode](https://woocommerce.com/document/stripe/customer-experience/testing/)
- **HPOS и владение.** Плагин использует Woo CRUD и явно декларирует совместимость после проверки HPOS. Сравнивать актуальный owner Woo с WordPress-сессией для аккаунта. В Engine только узкий короткоживущий grant с областью и последующей перепроверкой. Woo ключи служебного доступа не означают права покупателя. Сессия корзины не доказывает владение заказом. [HPOS recipe](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/), [WP REST auth](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/), [Store API Order](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/order/)
- **Исходящие логи.** Фильтровать на стороне источника до формирования canonical payload. Штатная диагностика Woo может хранить request/response body и заголовки. Для пилота использовать узкий webhook с непрозрачной ссылкой на запись, исключить секреты, raw order и credentials из диагностических логов, проверить настройку логов и их срок также на стороне Woo. [Webhooks v3 — Logging](https://developer.woocommerce.com/docs/apis/rest-api/v3/webhooks/#logging)

Устойчивый ACK Engine относится к конкретной принятой записи. Если стандартная активация подписки требует установочный ping, принять его отдельной операцией без полномочия и записи события. REST-сверка использует фиксированные UTC-окна `modified_after/modified_before`, `dates_are_gmt=true`, стабильный порядок по ID и пагинацию. Предложение для тестового профиля — запуск каждые 5 минут, верхняя граница с отставанием 2 минуты, overlap 15 минут. Не продвигать окно при неполной странице, `429`, отказе прав или ошибке. При изменении состава учитывать смещение, повторять окно и при необходимости сужать его. Кандидаты из списка перечитываются точечно. Отсутствие заказа и `404` не создают отмену. Эту процедуру нельзя использовать как доказательство полного журнала переходов. ## 6. Запись, повтор, безопасность и эксплуатация

1. **Приём.** Определить установку, проверить право, предел размера и класс входа, нормализовать. Устойчиво записать факт и задачи подписанных потребителей в одной транзакции. Уникальный ключ разрешает конкурентный дубль. Временный сбой до commit требует повторной подачи. После commit протокол может вернуть duplicate при потере ACK. Состояния журналирования и доставки различимы.
2. **Claim.** В короткой транзакции PostgreSQL выбрать ограниченную порцию due работ с `FOR UPDATE SKIP LOCKED`. Записать уникальный lease token и срок по времени БД. Не держать транзакцию на сетевом чтении. Обработка истёкшего lease снова доступна. Для завершения захватить барьер/запись в одном установленном порядке, повторно проверить срок, токен, цель, версию и ревизию. Устаревший worker не может зафиксировать эффект.
3. **Финальный commit.** Эффект тестового потребителя и `done` фиксируются одной транзакцией. Сбой до commit не оставляет результата. Сбой после commit перед ACK сохраняет результат и receipt. Внешние side effects вне пилота. Для них одной записи receipt было бы недостаточно: нужен отдельный контракт идемпотентности получателя.
4. **Повторы и пределы.** Предложение для стенда — до 25 элементов и 64 КиБ на пакет витрины, claim до 20 работ, первоначально не более двух воркеров на установку процесса, lease 60 секунд, максимум восемь повторяемых попыток c backoff до 5 минут. Числа калибруются на изолированном профиле. Временный отказ повторяется в рамках срока, постоянный — паркуется с кодом и ID. Повреждённый вход отклоняется до журнала, ошибка чтения уже принятой записи блокирует эффект и даёт диагностический сигнал. Ручной replay выбирает разрешённые ключи, проверяет барьер и lease, сохраняет прежние ключи. Для rebuild тестовой проекции требуется явная версия потребителя и scoped пересчёт, с прежними запретами удаления.
5. **Операции.** Метрики — accepted/duplicate/conflict/rejected по классу, возраст старейшей работы, lag durable-to-effect, overdue leases, retries/parked, ошибки подписи и rights, просроченные окна сверки, статус подписки, длительность commit и PostgreSQL locks/I/O. Границы tenant сохраняются в запросах, очередях, бэкапах, диагностике и индексах. Логи используют технические коды и разрешённые корреляционные ID. Код не выводит raw webhook, поиск, токены, billing, платежные поля и payload ошибок. Предложение нагрузочного прогона — 50 событий/с 10 минут с двумя магазинами и 20% повторов, затем остановить подачу и наблюдать дренирование. Записать оборудование, p95/p99, максимальный backlog и время его дренирования. Это начальный тестовый профиль, а не заявленный SLO. Рост проверять отдельно для одного горячего магазина и нескольких установок. Дополнительные брокеры, Redis и аналитическая БД не требуются для доказательства этих гарантий. [PostgreSQL SELECT](https://www.postgresql.org/docs/15/sql-select.html), [PostgreSQL INSERT](https://www.postgresql.org/docs/15/sql-insert.html), [Review Jobs как локальный образец claim](../../src/modules/reviews/prisma-review-jobs.ts#L43)

| Негативный сценарий | Проверяемый защитный результат |
| --- | --- |
| Браузер сообщает оплату или иной серверный переход | Browser ingress допускает только разрешённые типы наблюдений. Нет канонического перехода и задачи. |
| Tenant, пользователь или заказ принадлежат другому контексту | Связь задаётся сервером. Чтение снимка и запись повторно проверяют область и owner. Ответ не раскрывает наличие чужого заказа. |
| Старый подписанный webhook или одинаковый ID | Контекст источника, срок, стабильный ключ и минимальное значимое содержимое проверяются до записи. Если факт тот же, эффект один, если содержимое различается, фиксируется конфликт. Поздняя версия не меняет свежий снимок. |
| Replay после удаления или отзыв во время обработки | Барьер поколения устанавливается до очистки и сериализуется с фиксацией эффекта. Применение старого поколения закрыто на всех входах, включая relay, очередь и restore. |
| Маркетинг на данных чата / аналитики | Цель и право задаются доверенным контекстом. Replay, доступ и потребители применяют то же основание. Маркетинговый обработчик отсутствует в профиле. |
| Гостевая история прикрепляется к новому аккаунту | Выданные поколения не перепривязываются после logout/login. Допускаются только новые клиентские наблюдения в новом контексте. Гостевой grant ограничен чтением одного заказа. |

**Удаление и восстановление.** Постановка барьера + прекращение видимости при одной разрешительной границе, затем удаление записей журнала, work, производной, локального backlog и безопасных диагностических связей в области запроса. Для `subject:none` обеспечить индекс/маршрут удаления по авторитетно разрешённой ссылке на заказ внутри установки. Источник, способный повторно выгрузить запись, должен соблюдать барьер или отсечение периода. Минимальная информация о подавлении хранится не дольше утверждённого срока, выбранного так, чтобы перекрыть разрешённые replay и бэкапы. Тестовые снапшоты и бэкапы не открываются для обработки до применения свежих барьеров из независимого авторитетного источника. Если источник ещё не согласован, изолированный пилот может использовать закрытый restore с очисткой только Ingestion, новым поколением установки и отсечением старого backlog после отдельного согласования. Операционные заказы и действующие данные User Context имеют собственных владельцев удаления.

Гонки идут через два соединения, перезапуск через отдельный процесс, внешние провайдеры в локальных тестах — управляемые fixtures. Сервисы стенда с Qdrant остаются частью общей инфраструктуры. Прикладная логика Ingestion Qdrant и Redis не использует. Команда `contract` и smoke инфраструктуры дают свидетельства только о стенде. Новые тесты входят в будущую согласованную реализацию. [Shared Integration Test Environment](../../infra/integration/README.md#L44), [withServices](../../infra/integration/environment.mjs#L194), [Пример subprocess restart](../../infra/integration/agentic-memory-restart.mjs#L190)

**Проверка исходной ревизии.** Запуск Jest с `--runInBand --no-cache --runTestsByPath` для `order-checkout-prepayment`, `order-policy` и `payment-prepayment` дал 14 успешных тестов и 4 сбоя. Первые два набора прошли. В `payment-prepayment` четыре сценария завершились ошибкой `this.prismaService.payment.findFirst is not a function` до проверки переходов. Проверки шли с mock-зависимостями, без PostgreSQL, WooCommerce и YooKassa.

T13–T16 на fixtures и T22 проверяют разные уровни. Реальный Woo обязателен для доказательства auth, исходных payload и маппинга, test capture, поведения Checkout Blocks, HPOS, отключения подписки, восстановления recorded transition и гостевого чтения. Потерю до записи воспроизводит контролируемый разрыв в изолированном профиле. При условном C ожидается маркировка наблюдаемого расхождения без выдуманного перехода. При строгом O2 обязателен тест, подтверждающий восстановление точного перехода и в этом окне. Синтетический raw-адаптер пригоден для доказательства архитектурной заменяемости в проверенной области, а не для заявления поддержки реальной установки. [Portability Checklist](../../.agents/skills/support-engine-productization/portability-checklist.md#L134)

**Статусы на момент PLAN** — `MILESTONE_GATE: NOT VERIFIED`, `PORTABILITY_GATE: NOT VERIFIED`, `RELEASE_GATE: NOT VERIFIED`. Для milestone нужны M1–M5, матрица и регрессии объявленного объёма. Для portability нужен общий прогон на рабочем и независимом адаптерах без правок ядра и отдельная проверка клиентского wire независимым клиентом. Для release требуются рабочие профили и свидетельства установки, обновления, прав, бэкапа/restore, мониторинга, отказов и восстановления. Прохождение отдельно взятого contract run не повышает статус release.

## 9. Решения владельца продукта и блокеры

| Решение | Альтернативы, рекомендация и последствие отсрочки |
| --- | --- |
| O1. Среда Woo и разрешённый интеграционный плагин | Рекомендован изолированный WooCommerce 11.3.0 + Blocks/HPOS + исправленный Stripe Gateway 11.2.0, автоматический test capture. Допустима другая согласованная исправленная конфигурация после проверки. Без доступа и разрешения не выполнять реальную часть M4 и T22. |
| O2. Потери до долговечной записи Woo | По умолчанию требование непотери остаётся в силе. C годится при явном согласии на известное окно потери точного перехода. При строгой гарантии найти и испытать доказуемо атомарный или авторитетный долговечный журнал переходов. Без выбора блокируется реализация реального Woo capture и приёмка M4. |
| O3. Граница оплаты/checkout NextShop | Рекомендуется покрывать сохранённые PAID/CANCELLED, согласовать локальную коррекцию checkout, суммы оплаты и атомарной проверки PENDING при отмене как prerequisite и сохранить существующую внешнюю семантику. Если нужно обнаруживать capture без status-sync, утвердить отдельную серверную сверку с платёжным источником. Без решения M3 не закрывает гарантии. |
| O4. Семантика действий | Рекомендация — не публиковать отмену DRAFT и регистрировать `search.submitted` только на явном действии. Если нужен автопоиск, согласовать отдельную измеримую семантику и объём данных. Отсрочка оставляет открытыми соответствующую UI-часть M2 и cancel-path M3. |
| O5. Политика и восстановление данных | Рекомендуется изолированный пилот на синтетике с ограниченными сроками, раздельными целями и fail-closed восстановлением. Для возобновления с историей нужен независимый источник актуальных барьеров. Альтернатива для одноразового пилота — разрешённая scoped очистка и новая эпоха с отсечением старого backlog. Утвердить оператора удаления, сроки буфера/журнала/повторов/барьеров/бэкапов и профили и цели. Без решения не подключать персональную обработку и не открывать restore. |

Необязательные решения о пороге видимости, атрибуции, продуктовом User Signals и Recommendation Engine перенесены за рамки пилота. Рефакторинг авторизации существующего Cart API выделяется из этой задачи. Изменение поведения заказов выполняется только после согласования O3/O4.
