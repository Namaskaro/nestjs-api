# Agentic Memory V1 · технический план

Режим REUSABLE_PRODUCT. Утверждены A0–A2. Ветка feature/agentic-memory-v1. Backend baseline b23a3bb6ce0f9cc0a441cf499d4b1a61d6f77a16. Frontend baseline c36428a в отдельном checkout.

## Контракты

- Core принимает подтверждённые действия задачи с версией, ключом источника и доказательством. Маппинг NextShop выполняется адаптером до свёртки задачи Workspace. Изменения выводятся из успешных действий текущего хода. Полный Workspace, текст ответа и вывод модели не служат авторитетом памяти.
- PostgreSQL-модели ConsultationMemoryScope, ConsultationEpisode, ConsultationResumeOffer и ConsultationTurnReceipt. Scope проверяет магазин, владельца и источник. Эпизод связывает задачу, снимок, ревизию, ревизию содержимого, исход и время. Квитанция уникальна по принятому источнику и действию. Предложение уникально по значимой ревизии эпизода.
- Существующая транзакция допуска Chat присваивает монотонный номер клиентскому входу и поколение попытки. Retry использует тот же sourceMessageId и номер. Новый клиент передаёт необязательный clientMessageId. Сохранённый ответ связан с источником для дедупликации. Метки остаются серверными.
- После сохранения и Socket.IO публикации обычного ответа отдельная короткая Prisma-транзакция проверяет владельца, магазин, sourceMessageId, assistant Message, inputSeq, attempt, BOT, handoffVersion, memoryEpoch и ожидаемые ревизии. Она атомарно применяет изменения и квитанцию. Ошибка диагностируется и не влияет на обычный ответ. Пропуск после разрыва между отправкой и записью обнаруживается по отсутствию ожидаемой квитанции. Повтор LLM для восстановления памяти не нужен.
- Блокировка PostgreSQL на время LLM и SAVEPOINT не используются. Короткие изменения сериализуются Chat row lock. Ревизия или квитанция источника проверяется для зависимого от памяти Workspace до routing и при прямом входе после уточнения. Текстовый delta зависимого ответа удерживается до проверки актуальности. Если это требует пересмотра механизма исполнения графа, остановить зависимую работу и представить воспроизведение.
- Удаление и исправление меняют memoryEpoch. Удаление и очистка по сроку отсекают старые входы через purgedThroughSeq. Просроченные эпизоды исключаются при чтении и удаляются пакетами. Отдельные API GET, PATCH и DELETE проверяют владельца. Продолжение через chat:join и chat:consultation_resume_decision выдаёт одноразовую привязку. Пороги 7/14/90 суток проверяются по управляемым часам.

## Утверждённое продолжение

1. P1 — Core и прикладной слой памяти используют предметный транзакционный порт. NextShop нормализует доказательства доступа и допуска хода, Prisma реализует атомарность. Снимки v1 и v2 читаются одновременно. Запись v2 включается отдельно.
2. P2 — один контракт на NextShop и синтетическом каталоге ПК с иным форматом идентичности, источника и критериев. Реальный PostgreSQL для состояния, Qdrant для поиска NextShop.
3. UX1–UX2 — подтверждение из серверного состояния, явный поиск по прежним условиям, сохраняемое намерение начать новый подбор и исправление штатного WsJwtGuard. ProductAgent использует проверенную команду, привычный pipeline и актуальный каталог.
4. B0–B3 — области профиля и факты, тип события без транспорта, команда подтверждения владельца, атомарный отзыв и общий контракт. Тесты изоляции, конкурентных операций, сбоя, TTL, замены и удаления.
5. После каждого workstream выполнить MILESTONE_GATE. После регрессий, checklist и RELEASE_GATE поднять Live Preview на проверенных ревизиях.
