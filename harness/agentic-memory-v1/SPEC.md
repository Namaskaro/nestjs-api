# Agentic Memory V1 — Product Specification

## 1. Статус

**Status:** DRAFT  
**Project:** NextShop / Support Agent  
**Scope:** Short-term Memory Audit + Episodic Memory

Документ определяет требования к первой версии системы памяти AI-консультанта.

Техническая архитектура и план реализации должны быть подготовлены отдельно в `PLAN.md` после исследования существующей системы.

---

## 2. Цель

Разработать систему, позволяющую AI-консультанту использовать релевантный опыт предыдущих консультаций с покупателем.

Система должна различать:

- Текущий контекст консультации — Short-term Memory.
- Отдельные пользовательские задачи и их результаты — Episodic Memory.
- Устойчивые предпочтения пользователя — Long-term User Context.

В рамках V1 реализуется только Episodic Memory.

Для Short-term Memory проводится архитектурный аудит с возможными предложениями по улучшению.

Long-term User Context проектируется отдельно.

---

## 3. Существующая система

В NextShop уже реализован Product Consultation Workspace.

По предварительному описанию он содержит:

- Current tasks.
- Selections.
- Comparisons.
- Goals.
- Criteria.
- Feedback.
- Recent dialogue.

Workspace отвечает за состояние текущей консультации.

Он не должен автоматически считаться полноценной долговременной памятью пользователя.

Фактические возможности Workspace и связанных компонентов должны быть проверены по исходному коду.

# Часть I. Short-term Memory

## 4. Архитектурный аудит

Codex должен исследовать существующие механизмы хранения и использования контекста консультаций.

### 4.1. Область исследования

Необходимо изучить:

- Product Consultation Workspace.
- Существующий Support Graph.
- Хранение состояния графа.
- Механизмы восстановления состояния.
- Хранение истории диалога.
- Управление текущими пользовательскими задачами.
- Сохранение selections, comparisons, goals, criteria и feedback.
- Взаимодействие Workspace с ProductAgent.
- Существующие механизмы ограничения контекста LLM.

### 4.2. Вопросы для аудита

Codex должен определить:

1. Где фактически хранится каждый тип состояния?
2. Какие данные существуют только во время выполнения графа?
3. Какие данные сохраняются между сообщениями?
4. Какие данные восстанавливаются после перезапуска?
5. Как система определяет актуальную пользовательскую задачу?
6. Как обрабатывается смена темы?
7. Как предотвращается использование устаревших selections и criteria?
8. Есть ли дублирование между Workspace, историей сообщений и другими хранилищами?
9. Какие данные потенциально могут использоваться для формирования Episodic Memory?
10. Какие архитектурные ограничения необходимо учитывать при создании долговременной памяти?

### 4.3. Ожидаемый результат

Подготовить:

- Описание существующей архитектуры Short-term Memory.
- Схему реального движения данных.
- Описание жизненного цикла текущей консультации.
- Список подтверждённых архитектурных проблем.
- Предложения по улучшению.
- Оценку влияния изменений на существующего консультанта.

Необходимо отделять реальные дефекты от необязательных оптимизаций.

**Самостоятельный рефакторинг Short-term Memory не входит в утверждённый scope V1.**

Если Codex обнаружит необходимость архитектурных изменений, они должны быть отдельно обоснованы и согласованы.

# Часть II. Episodic Memory

## 5. Назначение

Episodic Memory хранит структурированную информацию о предыдущих пользовательских задачах и консультациях.

Основная цель — позволить консультанту учитывать прошлый опыт покупателя, когда он действительно относится к текущему запросу.

Эпизод не равен отдельному сообщению или целому чату.

Один чат может содержать несколько эпизодов.

Один эпизод может охватывать множество сообщений и продолжаться после перерыва.

---

## 6. Определение эпизода

Эпизод — логически связанная пользовательская задача, включающая:

- Цель пользователя.
- Существенные требования.
- Рассмотренные варианты.
- Принятые решения.
- Явные предпочтения и отказы в контексте задачи.
- Результат, если он известен.
- Статус завершения.
- Источники информации.

### Пример

**Цель:** выбрать кроссовки для ежедневной ходьбы.

**Рассмотренные товары:**

- Nike Mind 002.
- Другие модели из результатов консультации.

**Критерии:**

- Мягкая амортизация.
- Комфорт при длительной ходьбе.
- Отсутствие чрезмерно массивной конструкции.

**Результат:** пользователь выбрал Nike Mind 002.

**Outcome:** PRODUCT_SELECTED.

Этот результат не означает, что пользователь действительно приобрёл товар.

Факт покупки должен подтверждаться соответствующими данными заказа.

---

## 7. Жизненный цикл эпизода

Система должна поддерживать жизненный цикл отдельной пользовательской задачи.

Необходимо спроектировать механизмы:

1. Определения начала эпизода.
2. Связывания новых сообщений с существующим эпизодом.
3. Выявления независимой новой задачи.
4. Обновления контекста эпизода.
5. Определения завершения.
6. Фиксации результата.
7. Обработки незавершённых задач.
8. Возобновления ранее начатой задачи.
9. Исправления ошибочно определённых границ или результатов.

### 7.1. Явное завершение

Примеры:

- Пользователь подтвердил выбор.
- Пользователь сообщил об окончании консультации.
- Пользователь отказался от дальнейшего поиска.
- Пользователь сообщил, что подходящий вариант не найден.

### 7.2. Неявное завершение

Необходимо исследовать:

- Переход к другой независимой задаче.
- Длительное отсутствие активности.
- Прекращение обсуждения конкретной цели.
- Возможность существования нескольких активных задач.

Отсутствие активности само по себе не доказывает успешное завершение.

### 7.3. Возобновление

Если пользователь возвращается к предыдущей задаче, система должна уметь распознать соответствующий контекст.

Необходимо определить, когда следует:

- Продолжить существующий эпизод.
- Повторно открыть ранее завершённый эпизод.
- Создать новый связанный эпизод.

### 7.4. Архитектурное исследование

Codex должен сравнить варианты определения границ эпизода:

- Детерминированные правила.
- Существующие сигналы Workspace.
- Семантический анализ.
- LLM-классификация.
- Гибридный подход.

Для вариантов необходимо оценить:

- Точность.
- Сложность.
- Стоимость.
- Задержки.
- Риск ложного завершения.
- Возможность исправления решений.

Окончательный механизм утверждается в PLAN.md.

---

## 8. Результаты эпизодов

Система должна различать успешное завершение, отказ и неопределённый результат.

Предварительные категории:

- PRODUCT_SELECTED.
- NO_MATCH.
- ABANDONED.
- UNRESOLVED.
- USER_CANCELLED.

Это концептуальные категории, а не окончательный перечень enum.

Codex должен предложить модель результатов, соответствующую существующим бизнес-процессам.

Нельзя автоматически интерпретировать выбор товара как покупку.

Нельзя автоматически считать отсутствие ответа отказом от товара.

---

## 9. Структура Episodic Memory

Для каждого эпизода должны быть доступны следующие концептуальные сведения:

### Идентификация

- Идентификатор эпизода.
- Идентификатор владельца.
- Связь с исходной консультацией.
- Даты создания и изменения.

### Контекст

- Пользовательская задача.
- Цель.
- Значимые критерии.
- Рассмотренные товары.
- Существенные решения.
- Результат.

### Жизненный цикл

- Текущий статус.
- Способ определения завершения.
- Основание для результата.
- Возможность возобновления.

### Достоверность

- Источники информации.
- Различие между явными утверждениями и выводами системы.
- Время актуальности сведений.
- Возможность исправления или удаления.

Конкретные Prisma-модели, поля, отношения и индексы определяются в PLAN.md.

---

## 10. Хранение данных

Canonical storage — PostgreSQL.

Эпизодическая память должна сохраняться независимо от текущего состояния выполнения графа.

Необходимо обеспечить:

- Долговременное хранение.
- Разделение данных пользователей.
- Согласованное обновление.
- Защиту от дублирования.
- Восстановление после перезапуска.
- Возможность исправления и удаления.
- Прослеживаемость происхождения данных.

Не следует дублировать полную историю сообщений без обоснованной необходимости.

---

## 11. Поиск релевантных эпизодов

При новой консультации система должна определять, какие прошлые эпизоды действительно могут помочь.

Пример:

Пользователь просит подобрать удобные кроссовки для ежедневной ходьбы.

В памяти существует предыдущий эпизод с аналогичной задачей.

Консультант может использовать релевантные критерии и историю выбора.

### Требования

- Искать только эпизоды соответствующего пользователя.
- Учитывать текущую задачу.
- Исключать нерелевантные эпизоды.
- Не передавать всю память в каждый LLM-запрос.
- Ограничивать объём контекста.
- Не представлять прошлые предпочтения как неизменные факты.
- Предусмотреть отсутствие релевантной памяти.

### Архитектурные варианты

Codex должен сравнить:

1. Структурированный поиск PostgreSQL.
2. Поиск по метаданным и критериям.
3. Векторный поиск через Qdrant.
4. Гибридный поиск.

Qdrant не является обязательным компонентом первой версии.

Если PostgreSQL решает задачу достаточно хорошо, дополнительная векторная инфраструктура не требуется.

---

## 12. Интеграция с консультантом

Episodic Memory должна дополнять существующий Workspace, а не заменять его.

Необходимо определить:

- Когда обращаться к памяти.
- Какие эпизоды извлекать.
- Как оценивать релевантность.
- Как передавать результаты ProductAgent.
- Как избежать конфликтов с текущими критериями пользователя.
- Как предотвращать повторное использование устаревшей информации.

Актуальные явно выраженные требования пользователя имеют приоритет перед информацией из прошлых эпизодов.

Отсутствие доступной памяти не должно блокировать обычную консультацию.

Необходимо исключить возможность использования недоверенного текста памяти как управляющей инструкции агенту.

---

## 13. Управление памятью

Система должна поддерживать:

- Просмотр сохранённых эпизодов через определённый интерфейс доступа.
- Исправление ошибочных результатов.
- Удаление эпизодов.
- Запрет использования удалённых сведений.
- Проверку принадлежности памяти пользователю.

Необходимо отдельно спроектировать поведение при удалении или изменении исходной консультации.

Для V1 допускается ограниченный технический интерфейс управления, если полноценный пользовательский UI не утверждён.

---

## 14. Безопасность и изоляция

Память должна быть привязана к владельцу.

Запрещено:

- Получать эпизоды другого покупателя.
- Смешивать пользовательские контексты.
- Переносить гостевые данные между аккаунтами без подтверждённой привязки.
- Считать предположения достоверными фактами.
- Сохранять чувствительную информацию без определённой необходимости и разрешённого основания.

Необходимо определить политику хранения и удаления данных.

# Часть III. Long-term User Context

## 15. Отдельный будущий проект

Полноценный Long-term User Context не входит в Agentic Memory V1.

Для него предполагается отдельная система обработки пользовательских сигналов.

Потенциальные источники:

- Завершённые консультации.
- История заказов.
- События корзины.
- Просмотры товаров.
- Сравнения.
- Поисковые запросы.
- Явно указанные предпочтения.
- Повторяющиеся пользовательские действия.

Будущая система должна различать:

- Явно подтверждённые предпочтения.
- Косвенные поведенческие сигналы.
- Временные интересы.
- Устойчивые предпочтения.
- Противоречивые сведения.

Отдельно потребуется спроектировать:

- Каталог событий.
- Источники и способы доставки событий.
- Правила интерпретации.
- Приоритеты и достоверность сигналов.
- Обновление и устаревание профиля.
- Пользовательское управление контекстом.
- Ограничение объёма информации, передаваемой LLM.

В V1 запрещено создавать скрытую систему профилирования пользователя.

Возможность использовать эпизоды в будущем Long-term User Context должна учитываться архитектурно, но не требует реализации профиля сейчас.

## 16. Существующая архитектура

Необходимо сохранить совместимость с:

- Product Consultation Workspace.

Не допускается необоснованное переписывание работающих компонентов.

Существующий стек NextShop является исходной технической средой.

Предпочтительные компоненты:

- NestJS.
- TypeScript.
- Prisma.
- PostgreSQL.
- Существующая AI-инфраструктура.

Qdrant используется только при доказанной необходимости.

Новые внешние сервисы, брокеры сообщений и платные зависимости не добавляются автоматически.

Каждое существенное отклонение должно быть аргументировано и согласовано.

# Часть VI. Критерии приёмки

## 19. Short-term Memory Audit

**AC-01.** Исследована фактическая архитектура Workspace и связанных механизмов памяти.

**AC-02.** Подготовлена схема движения данных и жизненного цикла пользовательской задачи.

**AC-03.** Выявлены подтверждённые проблемы и архитектурные ограничения.

**AC-04.** Предложены обоснованные улучшения без самостоятельного несогласованного рефакторинга.

## 20. Episodic Memory

**AC-05.** Система различает отдельные пользовательские задачи в одном постоянном чате.

**AC-06.** Поддерживается создание эпизода и накопление относящегося к нему контекста.

**AC-07.** Поддерживаются явные и согласованные неявные механизмы завершения.

**AC-08.** Система различает успешные, неуспешные и неопределённые результаты.

**AC-09.** Поддерживается продолжение ранее начатой задачи без необоснованного создания дубликатов.

**AC-10.** Эпизоды сохраняются в PostgreSQL и доступны после перезапуска приложения.

**AC-11.** Обеспечена изоляция пользовательских данных.

**AC-12.** Поддерживается получение релевантных прошлых эпизодов.

**AC-13.** ProductAgent может использовать релевантную эпизодическую информацию при новой консультации.

**AC-14.** Использование памяти не приводит к неконтролируемому увеличению LLM-контекста.

**AC-15.** При отсутствии памяти консультант продолжает работать обычным образом.

**AC-16.** Поддерживаются исправление и удаление эпизодов с соблюдением ограничений доступа.

**AC-17.** Реализация не нарушает существующие пользовательские сценарии и бизнес-правила.

**AC-18.** Выполнены согласованные целевые и интеграционные проверки.

Методы проверки и конкретные тестовые сценарии должны быть определены в PLAN.md.

---

## 21. Out of Scope

В Agentic Memory V1 не входят:

- Полноценный Long-term User Context.
- Глобальный трекинг пользовательских событий.
- Аналитика просмотров товаров.
- Анализ всей истории корзины.
- Формирование устойчивого профиля предпочтений.
- Персонализация каталога на основании глобального поведения.
- Новая рекомендательная система.
- Полная переработка Workspace.
- Несогласованное изменение Support Graph.
- Production deployment.
